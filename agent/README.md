# Агент синхронізації 1С → Budvik

Служба Windows, яка встановлюється **на сервері 1С**, читає дані з 1С **виключно на читання** і надсилає їх на сайт Budvik.

## Чому саме так

Дані йдуть **назовні** — агент сам звертається до сайту через HTTPS. Тому:

- не треба відкривати порти в мережі компанії, не треба статичного IP чи VPN;
- 1С лишається недоторканою: агент виконує лише `GET`-запити, а користувач 1С має права тільки на читання;
- обрив інтернету не втрачає дані: батчі накопичуються в черзі на диску і доїжджають, коли зв'язок відновиться.

```
Сервер 1С (офіс)                          Railway
┌──────────────────────┐                  ┌────────────────────┐
│ 1С ──OData(localhost)│                  │ Budvik (Next.js)   │
│      ▲               │   HTTPS POST     │  /api/sync-ingest  │
│      └── Агент ──────┼─────────────────▶│         │          │
│          + черга     │                  │         ▼          │
│          + SQLite    │                  │    PostgreSQL      │
└──────────────────────┘                  └────────────────────┘
```

## Що синхронізується

| Дані | З чого в 1С | Куди на сайті |
|---|---|---|
| Групи номенклатури | `Catalog_Номенклатура` (`IsFolder=true`) | `Category` (дерево, `source="1C"`) |
| Товари | `Catalog_Номенклатура` | `Product` |
| Ціни (роздріб/опт) | зріз `ЦеныНоменклатуры_SliceLast` | `Product.price` / `wholesalePrice` |
| Склади | `Catalog_Склады` | `StockLocation` |
| Залишки по складах | `ТоварыНаСкладах/Balance()` | `LocationStock` + сума в `Product.stock` |
| Контрагенти | `Catalog_Контрагенты` | `Counterparty` |
| Документи | реалізації / надходження | `SalesDocument` / `PurchaseOrder` |
| Дебіторка | регістр взаєморозрахунків | `Counterparty.receivableBalance` |

Вмикається поетапно через `scope` у конфігурації.

## Встановлення

### 1. Передумови на сервері 1С

- **Node.js 20 LTS** — https://nodejs.org (перевірка: `node --version`)
- **nssm** — https://nssm.cc/download (покласти `nssm.exe` у папку `install\`)
- **Опублікована база 1С** з увімкненим OData-інтерфейсом
- **Користувач 1С** із правами **тільки на читання** (див. нижче)
- Вихідний доступ до інтернету по HTTPS (443)

### 2. Публікація OData в 1С

У Конфігураторі: *Адміністрування → Публікація на веб-сервері* → поставити галочку **Публікувати стандартний інтерфейс OData**.

Далі склад інтерфейсу задається одноразово (Конфігуратор або обробка):

```bsl
УстановитьСоставСтандартногоИнтерфейсаOData(Массив);
```

Перевірка з браузера на сервері:
```
http://localhost/<база>/odata/standard.odata/$metadata
```

### 3. Користувач 1С тільки для читання

Створити користувача `budvik_sync` з окремою роллю, у якій дозволено **лише читання** довідників Номенклатура, Контрагенти, Склади, потрібних регістрів і документів. Жодних прав на запис, проведення чи видалення.

Це головна гарантія безпеки: навіть якщо агент буде скомпрометовано, записати в 1С він не зможе.

### 4. Розгортання агента

```powershell
# У папці agent на сервері:
npm install
npm run build

Copy-Item config.example.json config.json
notepad config.json      # заповнити (див. нижче)
```

### 5. Перевірка ДО встановлення служби

Спершу сухий прогін — він нічого не змінює на сайті:

```powershell
node dist\agent.cjs --once --preview
```

У журналі має бути «Зв'язок з 1С OData встановлено» і «Зв'язок із сайтом встановлено».
Результати дивіться в адмінці сайту: **Адмін → ERP → Синхронізація**.

### 6. Встановлення служби

```powershell
# PowerShell від імені адміністратора
.\install\install-service.ps1

# Якщо в config.json є значення "env:ІМЯ" — задати їх для служби:
nssm set BudvikSyncAgent AppEnvironmentExtra SYNC_AGENT_SECRET=... ODATA_PASSWORD=...

Start-Service BudvikSyncAgent
```

## Конфігурація

Дивіться `config.example.json` — усі поля з поясненнями. Ключові:

| Поле | Що це |
|---|---|
| `ingestUrl` | адреса сайту, напр. `https://budvik.up.railway.app` |
| `agentId` / `agentSecret` | мають збігатися з `SYNC_AGENT_ID` / `SYNC_AGENT_SECRET` на сайті |
| `odata.baseUrl` | `http://localhost/<база>/odata/standard.odata` |
| `entities.*` | імена сутностей 1С — **залежать від конфігурації**, уточнюються через `$metadata` |
| `priceTypes.retail` / `.wholesale` | GUID видів цін з `Catalog_ВидыЦен` |
| `scope.*` | що саме синхронізувати — вмикайте поетапно |
| `schedule.intervalMinutes` | періодичність (за замовчуванням 20 хв) |
| `schedule.fullSyncCron` | нічна повна звірка — **не ставте на час бекапу 1С** |
| `preview` | `true` — нічого не змінює на сайті, лише рахує розбіжності |

Секрети краще не тримати у файлі: значення `"env:SYNC_AGENT_SECRET"` читається зі змінної середовища.

## Як це працює

**Кожні 20 хвилин** агент читає з 1С зрізи (каталог, ціни, залишки), рахує хеш кожного запису і порівнює з локальною базою SQLite. Надсилає **лише те, що змінилося** — зазвичай десятки записів, а не тисячі. Якщо змін немає, прогін навіть не створюється.

**Щоночі** (за `fullSyncCron`) виконується повна звірка: надсилаються всі записи плюс повний перелік активних ID. Сайт за ним визначає позиції, яких уже немає в 1С, і показує їх як розбіжності `MISSING`. **Автоматично нічого не деактивується** — рішення приймає адміністратор.

**Порядок важливий**: категорії й склади надсилаються раніше за товари й залишки, інакше нові товари потрапили б у категорію «Імпорт з 1С», а залишки не знайшли б складу.

## Безпечні за замовчуванням правила

- Ціни: зміна більш ніж у 5 разів **не застосовується**, а лише фіксується як розбіжність (захист від помилки в одиницях виміру).
- Описи товарів: сайт не дозволяє 1С затерти опис — він заповнюється лише якщо на сайті порожньо.
- Категорії наявних товарів **ніколи не змінюються** синхронізацією — ручна розкладка недоторкана.
- Контакти контрагентів лише доповнюються, порожнє значення з 1С нічого не стирає.
- Видалення рядків не відбувається ніколи.

## Експлуатація

```powershell
Get-Service BudvikSyncAgent                              # стан
Get-Content .\logs\agent-*.log -Tail 50 -Wait            # журнал
Restart-Service BudvikSyncAgent                          # перезапуск

node dist\agent.cjs --once                               # один цикл вручну
node dist\agent.cjs --once --full                        # повна звірка вручну
node dist\agent.cjs --once --preview                     # сухий прогін
```

Журнали — у `logs\` (14 діб), черга недоставлених батчів — у `outbox\`, стан hash-diff — у `state.db`.

## Типові проблеми

**«1С відхилила запит (401/403)»** — невірний логін/пароль користувача 1С або йому бракує прав на читання потрібного об'єкта.

**«Невірний підпис» від сайту** — `agentSecret` не збігається з `SYNC_AGENT_SECRET` на сервері.

**«Мітка часу поза допустимим вікном»** — годинник сервера 1С розійшовся більш ніж на 5 хвилин. Увімкніть синхронізацію часу Windows.

**Батчі накопичуються в `outbox\`** — сайт недоступний або відхиляє запити. Перевірте журнал; після 7 діб застряглі батчі видаляються автоматично.

**Товари потрапляють в «Імпорт з 1С»** — група 1С ще не синхронізована. Увімкніть `scope.categories` і дочекайтесь наступного циклу.

**Порожній `state.db`** (видалили файл) — наступний цикл надішле все заново. Це безпечно, лише довше.

## Скидання стану

Щоб змусити агент надіслати все заново, зупиніть службу й видаліть `state.db*`. Черга `outbox\` при цьому **не** видаляється — інакше недоставлені дані загубляться.
